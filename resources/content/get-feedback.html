Get feedback

The best ways to find out whether a design works, in order: watch real people use it, run automatic checks, and collect feedback in the product.

Nothing tells you more than watching someone use what you made. Automatic checks catch some problems quickly, and feedback in the product keeps finding them once the design is live. Use all three.

Test with real people

Give someone a task and watch them do it. Where they hesitate, go the wrong way or give up is where the design needs work.

  • Test with five people a round. Five people find most of the problems in what they test. Fix those, then test again with five more.
  • Give tasks, not directions. Describe the goal in the person's own words: "You want every new book by Priya Shah". Never name the page or the button.
  • Ask people to think aloud, and stay quiet. If they ask for help, ask what they would try next.
  • Write down what happened, not what you think of it: the task, what they did, and the words they used.
  • Pay everyone for their time.

Include people who use assistive technology

Every round includes people who use:

  • a screen reader, such as NVDA, VoiceOver or TalkBack
  • a magnifier or large text
  • voice control
  • a keyboard or switch access instead of a mouse

They test on their own devices with their own settings, because that is how they use every site. A problem they find often affects many other people too.

Snaglist can record each task as a series of steps with the technical details, so nothing is lost. Read Run a test session with Snaglist.

Run automatic accessibility checks

Automatic checks find problems such as low contrast, missing labels, missing alt text and headings out of order. They cannot tell whether a page makes sense to the person using it, so they never replace testing with people.

  • In this repository, tools/contrast.py checks every colour pair in every theme. Read Check contrast.
  • On a page, use a browser checker such as axe DevTools, WAVE or Lighthouse. Read Run automatic checks.
  • In your tests, run axe-core with Playwright, so a new problem stops a release.

To find problems and fix them in order, read Find and fix accessibility problems.

Collect feedback in the product with Snaglist

Snaglist is one file, under the MIT licence, that adds a 'Send feedback' button to any website or app. It uses this design system's tokens, so it matches Storyarr and Starboard. With it, people can:

  • report a bug or a UX problem
  • suggest a feature or an improvement
  • record a series of steps
  • run 'Check this page for accessibility problems'

Each report:

  • goes to GitHub issues, to an email address, or to the site's own server
  • carries the technical details a developer needs, such as errors, timings and the part of the page
  • keeps no personal information: emails, phone numbers, addresses and keys are replaced
  • is shown in full to the person before it is sent, and they can take parts out

When the computer is not online

Set-up often happens before a server is online. Snaglist can show a report as a QR code: people scan it with their phone's camera and send it from there, as the same pre-filled GitHub issue. A wizard in a terminal does the same, with the code drawn in the terminal. Read the rules in Terminal wizards, section 6.

Act on what you find

  1. Sort the reports: what stops someone finishing a task comes first. For reports on GitHub, read Triage reports on GitHub.
  2. Fix a shared component in this repository, not in the app. Read Make a change.
  3. Test the fix with the people who found the problem, when you can.
