TRex Design System: the component library

Design guide. Edit this guide on GitHub.

Version 1, 2 November 2026. One component library for both apps, so they share one design and one behaviour. It follows DESIGN-SYSTEM.md and the guides in this folder (CONTENT-DESIGN.md, HELP-WRITING.md and ACCESSIBILITY.md). File names in the tables in this guide are relative to the root of the repository.

Open components/index.html in a browser: every component in it works as it does in the apps. The component pages use the same header and menus as the apps. The main menu and search are in row 1, and the component groups are in row 2. Display opens the Display and accessibility slide-out, with theme, text size, reduced motion, high contrast, underlined links and wider spacing.

Slide-outs, menus, the phone menu and the dialog all work in the gallery.

Files

tokens.css Every colour, size, space and motion value, as role names, for Light, Dark, High contrast and High contrast dark, plus the display preference classes
components.css Every component, in @layer shared, using only the tokens
components.js The behaviour every component must have (menus, slide-outs, dialogs, phone menu, filter chips, copy, help, display settings), in plain JavaScript
icons.svg Lucide icons as an SVG sprite (<use href="#i-book-open">); tools/icons.txt lists them
fonts/ Atkinson Hyperlegible Next (OFL licence)
gallery.src.html The source of the component pages in components/, foundations/ and patterns/ (edit it, then run python3 tools/site.py)
contrast-report.txt Made by tools/contrast.py (not committed): measured contrast for every text and control pair in all four themes; all pass WCAG 2.2 AA
accent-report.txt Made by tools/check_accents.py --report accent-report.txt: every token pair the components draw, for every accent colour, in all four themes, including the menu hover fill and its edge; all pass WCAG 2.2 AA
areas/ Design boards for every area of both apps, using the library, with slide-outs where they fit
tools/build.py Turns into icons and <!--ICONS--> into the sprite for any *.src.html
tools/icons.py Rebuilds icons.svg from Lucide in Storyarr's node_modules
tools/sync.py, tools/paths.py Copies the library into both apps; paths.py says where the apps are (tools/paths.local.json, not committed)

Principles

  1. One design, two apps. Same tokens, same classes, same behaviour. An app may add its own components (charts on Starboard, the bookshelf on Storyarr) but builds them from the tokens.
  2. Accessible is the baseline. WCAG 2.2 AA in every theme. Controls and targets are 44px, and the focus ring is a visible 3px. Status is always in words plus a shape or icon, never colour alone.

Keyboard comes first. Everything works at 175% text and with wider spacing, and nothing moves when Reduce motion is active. 3. Mica, calm and dense enough. 6px corners, one typeface, card edges and rules in one colour, one accent colour, one primary button per view. The dashboard card is the model for panels, settings sections, tables, slide-outs and dialogs: a grey band on top, the body under it. 4. Things open where they make sense. Slide-out for the details or editing of one item in a list; dialog for a decision; page for something people return to. Read "Slide-out, dialog or page" in this guide.

Menu names

Names (TheMightyTRexUK, 4 November 2026: "Side menu, Level 1 menu and Level 2 Menu"):

  • Side menu: the icon rail on the left, in both apps: the logo with the app's name underneath, Search, then the sections. Starboard moves to the side menu (TheMightyTRexUK, 4 November 2026), with Library, Discover, Activity, System and Settings; read the Starboard menu board, areas/starboard-menu.html.
  • Level 1 menu: header row 1, the section's pages (Starboard: TV, Films, Radio, Books, Audiobooks). In Starboard it starts with the server's own name, up to 10 characters, as plain text with no icon.
  • Level 2 menu: header row 2, a page's own tabs (Starboard: My library, Series, Authors, Stations), only when the page has them.
  • On phones the header shows only the logo on the left, with no names (TheMightyTRexUK, 4 November 2026). The app's name and the server name stay for screen readers.
  • All three have icons. In the phone menu, only the side menu and the level 1 menu have icons; the level 2 menu stays under the header on phones.

Component Classes Notes

Visible word "Play"; screen readers hear the item and the app as well: "Play The Lost Valley in Jellyfin (opens in a new tab)". Always the full 44px button, never .btn--compact, as it can be the only way to play. Only where the app has the item and an address a browser can open is known: the app's address for browsers, or, when its only address is local to the server (127.0.0.1), the host the page was opened with and the app's port, as other Open links do; never an address only the server can reach, such as a container's name. Not in the app yet: no link, and words where it would be ("Not in Jellyfin yet"). Parts (22 November 2026)

Some components are large and few pages use them. They are marked as parts in the two source files. An app that counts every byte can then load them only where they are used (Starboard, lightweight first, DASH-507). The source files still hold every component: the gallery, the boards and the help centre load them whole, and so can any app.

The core is everything else, 59 KB compressed where the whole is 77 KB. The page banner and the tooltip stay in the core, as any page can need them.

For an app. Make a js/parts folder in the app's web folder, then run tools/sync.py. It writes the core as css/components.css and js/components.js, and each part as css/parts/<name>.css and js/parts/<name>.js. Without that folder the app gets the whole files, as before.

On a page that uses a part, load its styles after components.css. Load its script after components.js and the parts it needs, and before the page's own scripts. SharedComponents.setup() then sets the part up with everything else. Its functions are on SharedComponents as before (logView, showErrors, gauge and so on).

Marking a part. In components.css, inside @layer shared: /* part: name */ before the part's rules and /* /part */ after them, with the part's own Windows Contrast and less motion rules inside. In components.js: /* part: name; exports: a, b; setup: setupName; needs: other */ before and /* /part */ after. exports are the functions put on SharedComponents. SharedComponents.setup() runs setup, and you add first when it must run before the core's own set-up. needs names parts whose exports this part uses. A part may use only its own names, the helpers in SharedComponents.kit and what it needs.

A line outside a part that ends // part is left out of the core. python3 tools/parts.py checks all of this and lists the sizes. Run it after any change to a part. A component belongs in the core when any page may need it without warning. It belongs in a part when it is large and a page knows it will use it.

  • Remove drop shadows (TheMightyTRexUK, 23 November 2026, DASH-536: "add a setting to remove the all drop shadows with a note about it helping with performance").

  • An app applies the attribute before first paint, as it does the theme. The default follows the install: a small, Lite install starts with shadows off, and any other starts with them on. The default is the app's to set, and the library only provides the switch.

  • Every version is listed newest first and linked, as ## [x.y.z] (day month year). Dates are written as in CONTENT-DESIGN.md, not year, month, day.
  • Changes go under Added, Changed, Deprecated, Removed, Fixed and Security only. Withdrawn releases are marked [Withdrawn]. In-app release notes use the same six types.
  • Terminal wizards and feedback (TheMightyTRexUK, 5 November 2026). docs/TERMINAL.md sets how a wizard appears in a terminal.
  • A wizard is either boxed or plain. The boxed one has a heading box reading "App | step", a progress bar and a menu fixed on the bottom line with b Back, ? Help, f Feedback and q Stop. The plain one has numbered lines for screen readers and is never redrawn.
  • Help is a box over the step, and feedback is sent as a QR code sized to the window.
  • docs/WIZARD.md section 12 puts Snaglist on every wizard step and names the step. It has Show as a QR code for a computer that is not online yet.

Help centre (7 November 2026; the standard since 14 November 2026)

Every app's help is Markdown in its own repository, published as web pages by one builder, tools/help_centre/build.py, with this library's tokens, components, fonts and icons. Since 14 November 2026 every help centre uses the standard the owner chose (Starboard DASH-436): - the seven main items as top links - a hub with a side menu that folds (areas, groups, every article) - the journey, the newest thing and the problem solver card on the home page - the latest version beside the heading - articles with the flow chart first, then numbered answer cards - a problem solver page - plug-in mode for a plug-in collection

docs/HELP-WRITING.md section 11 is the full standard, with the flow chart format and the shape of help-centre.json.

App-only patterns (updated 26 November 2026)

Built from the tokens, used by one app, so not in components.css. Starboard builds about 420 classes of its own in web/css/app.css, apps.css, settings.css, system.css, dashboard.css, library.css, media.css and designs.css. These are the ones other pages are likely to need, so each is a candidate to move into the library, with a gallery entry and a board, when a second page needs it:

  • Starboard:
  • Settings tabs and sections: .settings-sections, .page--settings, and the General tabs (General, Alerts, Performance, Pictures).
  • The update list: .updates-table with its Check now button.
  • Where backups go: .place, .place-logo, .place-add, a list of places with a service logo.
  • Dashboard cards: .dash-grid, .dash-card, .guide-card, .spark-card, .dash-edit. Starboard draws its own sparkline because the library one cannot show gaps.
  • Slide-out wizards (the media server switch, backup places, cloud connect): a slide-out with its own "Step 1 of 3". docs/WIZARD.md describes the page wizard only.
  • Showing a secret once (a first password, an API key, recovery codes, a backup key): each is built on its own.
  • Folding table sections: .fold.
  • Poster cards: .lib-card, .network-card, .collection-card and .discover-card do what .media-card and .cover-card do in the library.
  • .access-change shows what Starboard can access, with the command to change it.
  • .job-run is a server job with Run now.
  • The storage charts use --media-*, which map to --series-*.
  • The release notes slide-out is .release-notes, opened from Release notes in the footer.
  • Storyarr (retired on 11 November 2026): the bookshelf and series views, and the library classes only it used (for example .book-row, .cover-card, .item-header, .list-detail and the logo slide-out).

  • Plug-ins: tv-station has its own time grid and drag-and-drop palette. Stallboard builds its own header, filters and tiles over the library, and redefines .shelf.

  • 11 November 2026: --font-heading (headings h1 to h4) and --color-rail (the side menu) are optional, for Starboard's styles. Unset, nothing changes.
